# Decisions

Judgement calls made during the build, the alternative considered, and why. Newest first.

## PR-1.S1: MCP server — transport shape, mobile gating, and JSON-RPC error semantics

**Decision:** the JSON-RPC method the server recognises for the tool call itself is `tools/call` with `params: { name, arguments }` (the MCP convention), not a bespoke per-tool method name. A later PR's tool just adds an entry to the same `tools` map passed into `McpServer`; the transport and dispatch (`src/mcp-protocol.ts`) never change. No `@modelcontextprotocol/sdk` (or any new runtime dependency) was added — the ticket-plan's constraint is "Node's own http and crypto modules; no new runtime dependencies." R2 added the rest of the handshake a standard MCP client needs: `initialize` (returns `protocolVersion`, `capabilities.tools`, `serverInfo`), `tools/list` (built from the same registry), and `notifications/initialized` (202, no body, per JSON-RPC's own notification semantics for a request with no `id`). `tools/call` results are wrapped in MCP's `{ content: [...] }` shape rather than returned as bare objects.

**Decision:** `McpTokenStore` is not keyed by node id the way `ApiHeadersStore`/`FolderSourcePathStore` are — there's exactly one MCP server per vault per device, so it holds a single `{ port, token }` pair under its own storage key (`atlas-mcp-server`), confirmed distinct from the other two stores' keys in `tests/unit/mcp-token-store.test.ts`.

**Decision:** on mobile, the whole MCP settings section (not just the toggle) renders a one-line "desktop only" note instead of the real controls. `McpTokenStore` itself is still constructed unconditionally in `onload()` (it's inert — just a `localStorage` wrapper, same risk profile as `ApiHeadersStore`), but `McpServer` (the listener) is only ever constructed, and only ever started, inside `if (!Platform.isMobile)`. This reading of F5 ("no listener, port or token work happens on mobile at all") treats "token work" as reading/writing the token for an actual request or UI display, not the mere existence of the lightweight store object — and hiding the settings section on mobile means the UI path that would do that reading never runs there either.

**Decision:** a request body over 1MB doesn't `req.destroy()` the socket — it keeps draining the stream to completion (discarding the bytes) so the handler can still send back a structured JSON-RPC error, per the fence item "never an uncaught exception or a dropped connection." Destroying the socket mid-stream would have violated that for the one edge case (oversized body) where it would have been the simplest implementation.

**Decision:** `McpServer.start()`/`stop()` both return a `Promise<void>` that always resolves, never rejects — a failed start (e.g. `EADDRINUSE`) is reported through the injected `notify`/`logError` callbacks, not an exception, so a caller (the settings tab's toggle, or `onload()`) never needs a `try/catch` around either call.

**Decision:** the Port field (R7) commits on blur/Enter, not on every keystroke — typing a multi-digit port one character at a time would otherwise bind-then-rebind through every in-range prefix along the way, and briefly latch the server off if some prefix happened to already be taken. A commit restarts the server from the user's saved intent (`settings.mcpServerEnabled`), not from `isRunning()`, so a restart after a prior failed start (stale `isRunning()===false`) still comes back on rather than staying silently off.

## Create from a meta folder (block, file or module): the menu, the body and the failure order

**Decision:** "Create" sits in a meta folder's right-click menu after "Rename folder". Obsidian's public `Menu` has no submenu API (`minAppVersion` 1.5.0, public APIs only), so choosing it pops a second small menu (Block, File, Module) at the same spot. It is still two clicks. Nothing else was added: no command, palette entry or setting.

**PR-1.F1 update:** the menu entry's label is renamed "Replace with…" (was "Create"), so it reads consistently alongside the later-added "Swap with…" entry right below it (plan G5/Q4). This is a label-only change — the operation described above (Block/File/Module chooser, dialog titles, body, failure order, replace-in-place) is unchanged, so "Create" below still refers to the operation and its dialogs, not the menu's wording.

**Decision:** every file Create writes has the body `# <name>` plus one trailing newline (Block, File and the Module's note alike). The name is trimmed when the dialog returns it, and validated again against the live vault root at create time, because the dialog can stay open while other things change. Block only needs a non-empty name (its file is named by ID); File and Module use the full name rules.

**Decision:** Create is not `addBlock` with a different name. `addBlock` opens the new file; Create must not. It shares only the ID generator, which now takes an injectable random source so the collision loop is testable. The ID loop never returns an occupied path and gives up after 100 tries.

**Decision:** the disk step runs first, then the meta node is replaced with the existing `replaceMetaNodeWithUnit`, then `data.json` is flushed. If a later step fails, Atlas deletes only what it created (file, then the folder if empty, then a pool folder it made if empty) and the meta folder is left as it was. Folders are deleted with `force`, since Obsidian 1.13.7 throws EISDIR on a plain delete.

**Decision:** an empty pool setting, or one that resolves to the vault root, makes Block refuse with a notice instead of writing into the root.

**Why:** the replaced node keeps its id, position, fold state, status governance and children, so nothing on disk moves and the row does not flash "missing" (the unit index updates from the vault create event before the node is swapped).

## PR 21: live-closed the drag-and-drop gap, and found two of its four ACs were stale rather than untested

The original F8 drag-and-drop ACs were marked deferred for one real reason: `xdotool`/X11 synthetic mouse events couldn't trigger native HTML5 drag-and-drop in the container this build used at the time. PR 12 and PR 20 both proved that's no longer true — CDP's `DragEvent`+`DataTransfer` dispatch drives real drag gestures directly, container or not. This PR used that to close every remaining "not exercised live (needs drag)" line rather than re-litigating whether it was possible.

Two of the four found, on inspection, weren't actually testable as originally written — not because of environment limits, but because the behavior they describe had already been superseded by a later PR, and nobody had gone back to update the AC's own wording:

- **"Expanded folder-unit internals → bucket manually promotes + places"** describes a gesture that doesn't exist anymore. PR 9 replaced inline-expanded internals with the Module Contents modal, and its own doc comment says plainly that dragging out from behind a modal backdrop is impractical — so internal rows were never made draggable at all (confirmed live: `draggable` reads `null`). PR 9 built a click-driven replacement instead (`promoteAndPlaceFlow`, same underlying `promoteAndPlace` operation) that nobody had actually tested, in any PR, until this one. Live-tested that instead of trying to force a drag that was deliberately removed.
- **"Dropping a unit onto a unit node → insert as sibling after it"** is from before PR 12. PR 12's own doc comment on `handleDrop` says dropping onto *any* row now always means "nest as a child," a deliberate simplification over a right-side/rest-of-row zone split — the sibling-insert behavior this AC describes, and the A6 bug fix logged against it, both belong to a model that no longer exists. Verified what the *current* code actually does instead (nests as a child) live, rather than trying to reproduce behavior PR 12 intentionally removed.

Lesson for future audits like this one: a checkbox left unchecked with an "environment limitation" note can silently drift out of date once the feature underneath it changes — the note explains why it wasn't tested, not that the described behavior is still accurate. Worth re-reading the actual current code before trying to test an old AC literally, not just running the drag and seeing what happens.

## PR 20 follow-up: two real bugs CDP testing couldn't catch, both found by Dan's own hands-on pass

Worth naming plainly, since it's now happened more than once in this build: **a real native browser drag-and-drop gesture and a CDP-synthetic one are not the same thing, and a bug that only breaks the former is invisible to the latter.** This PR's own extensive live-CDP drag testing (shift-range, multi-drag, the ancestor/descendant batching case, the module-icon restriction) all passed, because `dispatchEvent(new DragEvent(...))` fires the JS-level event listeners directly without ever engaging Chromium's actual native drag state machine — a state machine that, per well-documented browser behavior, aborts the whole gesture if its source element is removed from the document shortly after `dragstart`. `buildNodeDragPayload`/`buildInboxDragPayload` did exactly that: called `render()` (→ `container.empty()`) from inside a `dragstart` handler whenever the dragged row wasn't already part of the selection — which is the *common* case (dragging something you haven't multi-selected first). Every synthetic test in this PR happened to either drag an already-selected row (no render call on that path) or not notice the aborted gesture, since the synthetic path doesn't actually depend on the native session surviving. Only Dan's real mouse hit it, immediately, on the very first thing he tried. Fixed by simply not rendering from inside `dragstart` at all — the selection state still updates correctly; the visual catch-up happens on the next render regardless (which `handleDrop` already triggers).

The second bug (inbox scroll resetting to the top on every click) is a related lesson about scope, not about real-vs-synthetic input: `render()`'s scroll preservation was written once, early in the build (PR 9), against a single assumption — one scrollable container. F11 (PR 11) later gave the inbox its own second, independent scroll context for virtualization, and nothing updated the scroll-preservation logic to account for it. This sat as a latent, low-visibility gap for several PRs (the filter box already re-rendered on every keystroke, so it was theoretically always reachable) — PR 20 is what made it acute, since a plain click on an inbox row had never triggered a full re-render before this PR at all. Dan flagged it as a pattern he'd noticed recurring across multiple PRs, not something isolated to this one; worth remembering for any future work that adds a new independently-scrollable region to this view — `render()`'s scroll handling needs to know about it explicitly, it won't cover a new nested scroll context for free.

## PR 20: bucket/inbox multi-select — mutually exclusive selections, DOM-measured vs. captured-order range select, and a deliberately restricted module-icon gesture

F8's own spec is one line: "Multi-select with shift/cmd-click; drag moves the whole selection." Everything beyond that line is this PR's own judgement call, made explicit here rather than left implicit in the code.

**Bucket and inbox selections are mutually exclusive, not one combined selection.** A placed node (`moveNode`) and an unplaced ref (`placeUnit`) hit genuinely different operations at drop time, and mixing a "move this existing node" with "place this fresh ref" in the same drag isn't a real workflow anyone asked for — most apps with two distinct list panes (e.g. a sidebar and a main list) treat their selections the same way. Selecting in either list clears the other.

**Shift-range selection uses two different sources of "visible order" on purpose, not by oversight.** The bucket queries the DOM live at click time (`getBoundingClientRect().height > 0`) rather than tracking an order array during render — this means a collapsed folder's hidden contents and a filtered-out row are both correctly excluded from a range without a second structure to keep in sync with the tree. The inbox instead captures its own already-computed stable sort order once per render, because F11's virtualization means most inbox rows genuinely aren't in the DOM at any given moment — a DOM query there would silently miss whatever's currently scrolled out of view.

**Dragging an unselected row drags just that row, and resets the selection to it.** Standard file-manager convention: what you're dragging should always match what's visibly highlighted, not some other stale selection from three clicks ago.

**A node already nested under another dragged node in the same batch isn't moved a second time.** If both a meta folder and one of its own children happen to be selected together (a somewhat unusual thing to do, but reachable via cmd-click), moving the parent already carries the child along; moving it again separately afterward would yank it back out as a flattened sibling — almost certainly not what dragging them together was meant to do. Filtered out via a `nodeContainsDescendant` check against the rest of the batch before the move loop runs.

**The module-icon real-disk-move gesture (PR 10) is deliberately restricted to a single-item drag.** Everywhere else, "drag moves the whole selection" is a pure bucket-tree/ref-placement operation — never touches disk (Part 7). The module icon is the one exception that does. Bulk-filing several selected items into a real folder on disk at once is a materially different, riskier gesture than the one-at-a-time, always-confirmable version this build already shipped and reviewed — so a multi-item drag onto a module's icon is a no-op rather than silently (or even with a confirm dialog covering several files at once) becoming a new bulk-disk-mutation feature nobody asked for. A multi-item drag still works normally on the *rest* of that same row — meta-nesting under it organizationally, never touching disk — only the icon's own drop zone is restricted.

**Right-click and Delete/Escape got different treatment.** Right-click stays completely unchanged — always the single right-clicked row's own context menu, selection state untouched either way — since the spec bullet only mentions click-to-select and drag, not batch context-menu actions, and building one wasn't asked for. Delete (already existing for a single focused row) and Escape (new) *did* get extended to the whole selection, since they're the two keyboard actions that were already there and directly parallel what drag now does — a natural, low-risk extension of an existing pattern rather than new scope.

**A real test-harness false positive, caught and ruled out before trusting the result.** An early cmd-click toggle-off test (dispatching several clicks back-to-back with zero delay between them) appeared to fail — the toggled-off row stayed selected. Traced it to `render()`'s `container.empty()` running synchronously ahead of the previous click's async rebuild, so the second click's `querySelector` for the next test target returned nothing and the assertion silently drifted. Re-ran with realistic ~150ms spacing between dispatches (a real mouse physically cannot click two different rows inside one JS tick) and the toggle worked correctly. Same category of issue as PR 17's dropdown-default false positive — noted here again since it's now happened twice with the same root cause (rapid-fire synthetic events outrunning an async re-render), worth remembering for whoever tests the next PR with CDP.

## PR 19: truncate/hide filter interaction resolved during build; expand/collapse ported from the reference plugin, the gesture wasn't

TASKS.md flagged the filter-box interaction as "not yet grilled — flag for Dan if it's not obvious once in the code." It turned out to be obvious: PR 9 (issue 6) already established the exact principle needed — a folder that would otherwise fold away a filter match gets force-revealed instead, via `subtreeHasMatch`. Extending that same principle to hide/truncate (a node that itself matches, or contains a match, always renders individually, bypassing both) is a direct application of precedent already reviewed and shipped, not a new judgement call — so resolved it during the build rather than blocking on Dan, per TASKS.md's own allowance.

Checked the reference plugin's actual live container build for the rest of the design (grouping threshold, label format, expand behavior) before writing any code — same standard used for every other status feature ported into Atlas this batch. Two things carried over directly: grouping only kicks in once at least two direct children share a truncation-enabled status (collapsing a lone item into a "summary" of itself has no purpose), and the placeholder's label falls back to a pluralized status label when the governor hasn't set a custom one ("Idea" → "Ideas", "Items" if the status itself has no label at all) — ported `pluralizeStatusLabel` from the reference plugin verbatim, same fallback rules.

One thing deliberately **not** ported: the reference plugin expands/collapses a group via a double-click on a member's own dot (needs its own mousedown-timing/DOM-patch machinery, since it's layered on top of Obsidian's native file explorer). Atlas already gives a single click on a status dot a real, shipped, reviewed meaning — opening the change-status popup (PR 16) — so binding a second, timing-based meaning to the same target would create exactly the kind of interaction collision this build has been careful to avoid elsewhere (e.g. PR 16's own module-icon click resolution). Expand/collapse state is ephemeral (an in-memory `Set` on the view, not persisted), matching every other fold-state field already on `AtlasExplorerView` — a freshly reopened bucket starting collapsed is the expected, unsurprising default, same as any other fold state in this plugin.

## PR 18: move/duplicate/meta-nest status semantics were already correct by construction — this PR mostly verified, not built

Going in, PR 18's four ACs (own status survives a move, inherited status re-resolves or drops per the new parent, a duplicate keeps its original's status, meta-nesting picks up inheritance) read like they'd need new resolution code specifically for "what happens after a move." They didn't — `resolveNodeStatus`/`findGoverningAncestor` (PR 17) never cache anything about a node's position; they always walk a fresh `ancestors` array built from the tree's *current* shape at render time. `moveNode` (`views.ts`) relocates the actual `ViewNode` object, not a copy, so every own-field travels with it for free. The only place this *could* have broken was `duplicateNode`'s `cloneNode`, which did a shallow `{ ...node }` — fine for scalar fields, but left `applyTo`/`truncatedStatuses` (both objects) shared by reference between a clone and its original. Checked every write site before deciding whether this was live-bug or just latent: every one of them (`modals.ts`, `updateStatusGovernance`) replaces the whole object rather than mutating it in place, so nothing actually broke today — but a clone silently entangled with its original is exactly the "looks fine until someone adds a mutating write path" trap this build has hit before (the PR 14 stale-swatch-closure bug, the PR 16 popup-listener-leak), so fixed it anyway rather than leaving it as a landmine.

Verified all four ACs against a real 3-level test tree built directly through `ViewsManager` (not just read through the code): an explicit status (`explicitStatusId`) survives being moved to a different governor using the same set, and correctly shows nothing (while keeping the field intact) once moved somewhere with no governor at all — "moves with it" means the assignment survives, not that a governor materializes to display it. A purely-inherited item re-resolves correctly through an intermediate non-governing level and correctly loses its display under a non-governing parent. A duplicate's `applyTo`/`truncatedStatuses` snapshot the original's values at duplication time and are then independently mutable (mutated the clone's copy directly, confirmed the original's was untouched). Meta-nesting a plain item via `moveNode` (the same call `handleDrop`'s meta-nesting path makes) under a non-governing folder whose own parent inherits picks up that inherited status immediately. Also screenshotted the whole rendered tree at once and confirmed the dots matched the data-model results exactly, not just individual `resolveNodeStatus` calls in isolation.

## PR 17 follow-up: three modal UX bugs, all found by Dan directly interacting with the real UI

**None of these were visible to CDP-driven testing, and that's worth naming plainly rather than treating as a fluke.** All three (a toggle visibly jumping position, scroll resetting on every change, a dropdown appearing empty in some interaction sequence) are about how the modal *feels* to use — layout reflow, scroll continuity, timing — not about whether the underlying data ends up correct, which is what `data.json` inspection and DOM-state assertions actually check. A synthetic `.click()` dispatched via CDP updates state correctly regardless of whether a real mouse click would have *looked* jarring doing it. This isn't a reason to trust automated testing less — it caught real data-correctness bugs earlier in this exact PR that a visual pass alone might have missed — it's a reason the two need each other, and why Dan's own hands-on pass stays a mandatory step in this process rather than something automated testing could someday replace.

**The truncate-row jump: fixed by making the layout static, not by reordering it.** The instinct might be to just swap which element gets added first (label before toggle) and call it done — that alone would still leave a `DOM insertion/removal` happening every time truncation toggles, and *something* growing or shrinking a right-aligned control group will always risk moving its other members, regardless of order. Dan's own suggested alternative — render the field unconditionally, just disabled — removes the appearing/disappearing event entirely, which is the actual root cause, not the order it happened to occur in.

**Scroll preservation required checking which element actually scrolls, not assuming `contentEl`.** Obsidian's `Modal.contentEl` (`.modal-content`) is the element most code reaches for, but it turned out to have `overflow-y: visible` and grow to its natural height — `modalEl` (`.modal` itself) is what actually has `overflow-y: auto` and a real scrollbar. Checked live via `getComputedStyle`/`scrollHeight` comparison before writing the fix, rather than assuming `contentEl` was right because it's the more commonly-referenced property.

## PR 17: root-level assignment and per-item assignment share one ancestor-walk, not two code paths

**Decision:** the view root became a `StatusGovernance` too (the same interface `ViewNode` already implements), not a special-cased parallel mechanism. Rendering threads an `ancestors: StatusGovernance[]` array now instead of a single `parentNode` — `ancestors[0]` is the nearest governor candidate (a real `ViewNode` for anything nested, or the `View` itself for a top-level item), and the walk just keeps going outward. Root-level assignment (this PR's own new AC) and ordinary per-item assignment (PR 15) resolve through the exact same function with no branch distinguishing "is this the view root" from "is this a regular node" — the view simply always sits at the far end of every ancestor chain.

**Why this mattered more than it might look:** the alternative (a separate `resolveRootStatus` function, or an `if (isRoot)` branch inside the existing one) would have meant inheritance-to-subfolders logic had to be written and tested twice, once for "cascading from a node" and once for "cascading from the root" — exactly the kind of duplication this codebase has already been burned by more than once (`renderFoldableChildren`'s own extraction, `resolveNodeStatus`'s own doc comment referencing PR 13's near-identical `unplaceUnit`/`unplaceNode` split). One function, one set of tests, one place inheritance precedence can go wrong.

**Inheritance precedence: nearest *governor* wins, not nearest *reaching* governor.** Walking up from a node's direct parent, the first ancestor that actually has `statusEnabled`+`statusSetId` set is the one in effect — full stop. If that nearest governor doesn't itself reach this deep (it's not the direct parent, and its own `inheritToSubfolders` is off), the node shows nothing; the walk does *not* continue past it to see if some more distant ancestor's `inheritToSubfolders` might reach instead. This is standard "closest explicit ancestor wins" precedence (the same shape CSS inheritance has), not "does anything anywhere above me apply." Verified live with a three-level tree specifically built to distinguish the two: a mid-level item with its own assignment correctly overrode its grandparent's status set for its own children, even though the grandparent's own `inheritToSubfolders` was on and would otherwise have reached that deep.

**"Apply statuses to" — grilled with Dan, since the reference plugin only has two flags (`applyToFiles`/`applyToFolders`) and gave no hint how to map onto Atlas's richer four-way split.** Confirmed with Dan directly: "block/file/module/folder" means block, file, module (a real on-disk folder — Atlas's own name for a folder-unit, there's no separate "plain folder" ref kind), and **meta folder** (the organizational, no-disk-presence kind) for the fourth. Defaults to `true` for any unset field, matching the reference plugin's own default of applying to everything unless told otherwise — a governor created before this PR existed keeps working exactly as it did, not silently narrowing to nothing.

**Hide-completed/hide-cancelled and truncate-statuses are capture-only in this PR, by design, not an oversight.** PR 19's own description ("wiring PR 17's settings into the actual live rendering — this PR only captured the settings") already establishes this split; inherit-to-subfolders and apply-to are the two fields that had to be functionally real in *this* PR specifically, since they change what a row's dot already looks like today, not a future filtering pass.

**Real bug caught by this PR's own live testing, not shipped:** the rewritten modal's "Status set" dropdown showed a cosmetic default (the first available set) via `setValue`, but nothing actually wrote that default into the governance object being saved unless the user touched the dropdown themselves. Turning the master toggle on without ever touching the dropdown persisted `statusEnabled: true` with `statusSetId` left `undefined` — reproduced exactly this way testing root-level assignment (enable, close, no dot anywhere). Fixed by eagerly defaulting and persisting `statusSetId` in the modal's own render pass the moment sets exist and none is chosen, rather than waiting on an interaction that a real user testing the "just flip the master toggle" path would never think to perform.

## PR 15 follow-up: the open targeting question was answered — descendant-governing, not self-governing

**Resolved:** the "not resolved, left open for PR 16" question directly below turned out not to need PR 16 at all — both the reviewer (independently, citing the same spec line) and Dan himself (via live testing) landed on the same answer before PR 16 ever started. **Why this wasn't caught before it reached Dan:** the technical-check/live-testing pass verified the *mechanism* worked (toggle → dot appears, live, correctly colored) without checking it against the *specific wording* of the original spec attachment — a rendering bug wouldn't have shown this, since everything genuinely did work, just for the wrong node. This is the same class of miss as PR 13's "handles a duplicate but mishandles what it carries" note: the code did what it was built to do, it just wasn't checked against the one sentence that said what it should have been built to do. Worth carrying forward: for any PR ported from a written spec (the item-5 attachment, in this case), re-read the actual spec sentence for the exact mechanic being built, not just the TASKS.md paraphrase of it, before calling live verification complete.

**The fix, mechanically:** `resolveNodeStatus` itself didn't need to change — it already just "reads a node's own `statusEnabled`/`statusSetId`". What changed is *which node* gets passed to it during rendering: `renderNode`/`renderNodeList` now thread a `parentNode` parameter through the render tree, and a row's displayed status resolves against its *parent*, not itself. The governing node's own row is unaffected by its own assignment. Also added the `node.children.length > 0` gate on the "Statuses" menu item itself — foreshadowed by PR 16's own AC wording ("if an item has no children, it gets no 'Statuses' option at all"), which in hindsight was already describing this exact model, not a PR-16-only addition.

**A second, independent bug Dan's testing caught in the same pass:** the "Statuses" modal let the master toggle be switched on with zero status sets in existence, silently persisting `statusEnabled: true, statusSetId: null` — a combination that can never resolve to a visible status, with nothing telling the user why. Fixed by disabling the toggle itself (not just the status-set dropdown, which was already correctly disabled) whenever no status sets exist, with inline text explaining what to do first. This is a plain oversight, not a spec-reading miss like the targeting bug above — logged separately because the fix and the lesson are different in kind.

## PR 15: status assignment is per-node, not per-ref — so it can't reach inbox rows yet

**Decision:** PR 15's spec describes a "minimal assignment mechanism" (master toggle + status-set picker, opened via right-click → "Statuses") without specifying *what* the assignment attaches to. Two options existed: key it by `UnitRef` globally (like `manualPromotions`), or store it directly on the `ViewNode` that gets right-clicked (like `collapsed`). Went with per-`ViewNode`.

**Why:** PR 17's own AC talks about status as something that can be *lost* or *need to travel*: "Moving an item that has its own status assigned: the status moves with it" and "does a duplicated item... keep the same status? default assumption: yes, since it's a full clone." Neither sentence makes sense if status were a flat, ref-keyed global fact — a ref-keyed status wouldn't need to "travel" with a move (the ref doesn't change), and a duplicate would trivially *share* the exact same status rather than needing an explicit decision about whether to copy it. Both ACs only make sense if a status assignment belongs to a specific node instance, exactly the same way `collapsed` already does, and exactly the same way PR 13 already established that two duplicate placements of the same unit are structurally independent. Storing it as `ViewNode.statusEnabled`/`statusSetId` keeps this PR consistent with that precedent instead of introducing a second, differently-scoped persistence pattern.

**The tradeoff this creates, accepted deliberately:** inbox rows are pure `UnitRef`s with no `ViewNode` — until something is placed into a view's bucket, there's nowhere to hang a per-node assignment. So in PR 15, only bucket rows (units and meta folders) can have a status; an inbox row never shows a dot, full stop, regardless of what it's "supposed" to represent. This isn't called out as a gap in the spec's own edge-case list (only "item with no status assigned keeps its normal icon" is), so it's logged here rather than left silent. If inbox-row status display is actually wanted later, it would need a second, ref-keyed lookup layered on top — a real design change, not a bug fix, and not something to guess at now.

**Update — resolved, see the newer entry above:** this was originally left open pending PR 16. It didn't make it that far — Dan's own live testing (and the reviewer, independently) settled it same-day as descendant-governing, and PR 15 itself was reworked accordingly rather than waiting for PR 16.

## PR 13 follow-up: reviewer (A16) caught a third one-node-per-unit-per-view spot the technical check missed

**Decision:** the PR 13 technical check (above) found and fixed two spots; the Atlas reviewer's pass on the finished PR found a third, same-day, before merge: `placeUnit`'s "already placed elsewhere in this view — move it" branch. It used to splice the existing instance out and build a **brand-new** node (`children: []`) at the target location — the exact same discard-and-recreate mistake PR 12 already fixed once for `handleDrop`'s reparent path, and PR 13 itself already fixed once for `unplaceUnit`. Unreachable before duplication existed (a ref could only ever have one placement per view, so "already placed" and "the one I'm about to lose children from" were never the same instance in a way that mattered); duplication makes it directly reachable — duplicate a unit with meta-nested children, then use "Place in view…" back onto that same ref, and the first duplicate's subtree silently vanished. Fixed with the same remedy as the other two: move the real node in place (same id, children travel with it) instead of discarding and recreating it. Verified live via `viewsManager.placeUnit(...)` called directly against a unit with two meta-nested children — moved node keeps its original id, both children present after the move.

**Why this one slipped past the PR's own technical-check grep:** the check was framed around "does this assume at most one placement exists" — `placeUnit`'s already-placed branch does the opposite, it explicitly *handles* the multi-instance-capable case (that's exactly why it exists), so a grep for the missing-case pattern didn't flag it. The actual bug wasn't in the *existence check*, it was in *how* the existing instance got relocated once found. Worth remembering for PR 14 onward: "assumes uniqueness" and "handles a duplicate but mishandles what it carries" are different bug shapes, and the second one doesn't show up in a grep for the first.

## PR 13: allowing duplicate refs exposed two more places that assumed one-node-per-unit-per-view

**Decision:** the grilled spec explicitly asked for a technical check — grep the codebase for anywhere that assumes a unit has at most one `ViewNode` per view, now that duplication makes that false. Two real spots turned up, both fixed here rather than filed separately, since they're a direct consequence of this PR's own feature.

**`unplaceUnit` found the first matching ref and stopped.** Fine when at most one instance could ever exist; wrong once two can — right-clicking a *specific* duplicate's "Remove from view" could silently act on a *different* instance (whichever the tree-walk found first), not the row the user was actually looking at. Split into two functions with distinct, honest semantics instead of trying to make one function serve both: `unplaceNode(viewId, nodeId)` removes one exact instance by id — what "Remove from view," the Delete key, the missing-ghost "×" button, and drag-to-inbox-unplace all actually mean (four call sites switched to it). `unplaceUnit(viewId, ref)` keeps its old name but now removes *every* matching instance in a loop, since its one remaining caller (`handleAddToModule`'s demotion cleanup, when a moved file stops being a recognized unit) genuinely wants "purge this ref everywhere it appears," not "remove one specific row" — leaving it ref-based-but-single-match would have left stale duplicate placements behind after a demotion.

**`getPlacements`/`pathToRef` also stopped at the first match per view.** The "placed in…" row tooltip would have silently under-reported a unit duplicated to two spots within the *same* view, showing only one of the two placements. Renamed to `allPathsToRef`, collects every match in the subtree via unconditional recursion instead of returning as soon as one is found.

## PR 14: status data model shape, and a status-row layout it took two live bugs to get right

**Decision:** port `StatusDefinition`/`StatusSet`/color-palette 1:1 from `danrfletcher/obsidian-file-folder-status-icons`'s own model (`id`/`label`/`color`/`isCompleted` on a status, `id`/`name`/`statuses`/`defaultStatusId` on a set, a flat hex-string palette array) rather than inventing a new shape — this is a foundation PR specifically meant to carry the reference plugin's model into Atlas, not redesign it. **Two real layout bugs found and fixed during live testing, not left as known gaps:**

1. The first pass put two full toggle+label pairs (Completed/Cancelled) plus four extra-button icons (make default, move up, move down, delete) directly on each status row. The reference plugin sidesteps this with a dedicated "more actions" popup utility (`openChoicePopup`) it built for exactly this problem; rather than porting a second popup system, everything except the swatch/label/badges was folded into a single "more actions" menu using Atlas's own existing `Menu` import (already used by the explorer's row context menus). 2. Both were caught by measuring actual rendered dimensions live in the container rather than trusting the code to look right — the settings panel is a fixed-width native pane, not a page that reflows, so an overflow here doesn't have the safety net a responsive web layout would.

## PR 12: two pre-existing bugs found while unifying the data model, fixed as part of this PR rather than filed separately

**Decision:** while implementing meta-nesting-via-drop, reading `handleDrop`'s reparent logic closely (necessary anyway, since it's the exact function this PR needed to generalize) surfaced two real bugs that predate this PR entirely. Fixed both here rather than opening them as separate follow-ups, since PR 12 is what makes them newly reachable/consequential and the fix sits directly alongside the code this PR was already rewriting.

**Bug 1 — `unplaceUnit` discarded children.** "Remove from view" and the Delete key both call `unplaceUnit`, which used to `splice` the target node out and drop its `children` array on the floor — `deleteMetaFolder` already promotes a deleted meta folder's children up a level instead of losing them, but `unplaceUnit` never got the equivalent treatment. Harmless before this PR (a unit could never have children to lose), silently data-destructive after. Fixed to match `deleteMetaFolder`'s own pattern exactly.

**Bug 2 — reparenting an existing node went through the wrong function, and silently didn't work at all for a dragged meta folder.** `handleDrop`'s `payload.kind === "node"` branch (an *existing* tree node being dragged, not a fresh unit from the inbox) called `placeUnit(viewId, ref, parentId)` — but `placeUnit` builds a **brand-new** `ViewNode` with `children: []`, then a second `moveNode` call was layered on top to actually reposition it. Two problems: (a) for any node with real children, this silently deletes them (a fresh node can't carry over what the old one had) — impossible before PR 12, guaranteed to happen constantly after it, since reordering/reparenting an already-nested unit is exactly what this feature is for; (b) `placeUnit` looks a node up by `UnitRef`, which a **meta** folder doesn't have — dragging a meta folder onto anything computed a fallback garbage ref (`{kind:"file",path:""}`), which `placeUnit` then inserted as a phantom empty-path unit node into the tree, while the actual dragged meta folder was never moved at all. This second bug already existed for every meta-folder drag before PR 12 — it just never had an automated way to get caught (drag-and-drop in this build has only ever been verified by Dan's own hands, and apparently this exact gesture — dragging a meta folder *onto another node*, as opposed to onto the bucket root — never came up in his passes so far).

**Fix:** for `payload.kind === "node"`, call `moveNode` directly with the dragged node's own `id` — no ref, no `placeUnit`, no second node object. `moveNode` already reparents the *actual* node in place (splice out, splice into the new parent), which correctly carries over `children`/`collapsed`/`id` and works identically for meta and unit nodes, since it was never ref-based to begin with. `placeUnit` now exists purely for its actual purpose: bringing a *fresh* unit in from the inbox, where there's no existing node to preserve.

Also found and fixed the same "only walks `meta` children" gap in two smaller spots while auditing every `node.type === "meta"` check in the codebase for this PR: `pathToRef` (the "placed in…" row-tooltip breadcrumb builder) and `collapseAll`. Both would have silently ignored a unit nested under another unit — the tooltip would say "not placed anywhere" for a unit that very much was, and "Collapse all" would leave it expanded. Neither is possible to trigger without this PR's own feature existing, so these aren't "found a bug in old code" the way the two above are — more "finished the job the same audit already started."

## PR 11: bucket/inbox content always renders regardless of collapsed state — same tradeoff meta-folders already accept

**Decision:** fixing the bucket/inbox section animations required a bigger structural change than the filter-reveal fix (which just needed the instant-toggle-then-delayed-render trick) — their content used to only exist in the DOM at all while expanded (`if (this.bucketCollapsed) return;` before any content was created), so there was no persisting element for a CSS transition to animate. Fixed by always rendering their content into a dedicated wrapper and letting CSS (`grid-template-rows`, the same technique meta-folders use) handle the visual hide, not a DOM-presence check — which means a collapsed bucket/inbox now pays the same rendering cost an expanded one does, whether the user can currently see it or not.

**Why this is an acceptable tradeoff, not an oversight:** meta-folders already made exactly this same call in PR 8 (their children always render regardless of collapsed state) without it being controversial — a collapsed section that can't animate open smoothly isn't a real alternative once Dan's asked for the animation directly. For the inbox specifically (the one case where this could matter — thousands of rows, per F11's scale target) the actual DOM footprint stays bounded regardless: F11's virtualization already limits rendered rows to whatever's in the visible scroll window, so "always render" only adds back the `Promise.all` resolve-and-sort pass across every unit, which F11's own benchmarking already clocked at 2-10ms for realistic vault sizes — not the kind of cost that's worth keeping a section permanently un-animatable to avoid.

**A second, separate wrinkle for the inbox only:** its section container already had `flex: 1 1 auto` (PR 9 issue 3, so it fills whatever vertical space is left in the panel) — flex-grow doesn't know or care that a collapsed section's content just went to zero height, so without a fix a collapsed inbox would still stretch to fill all remaining space, just as an empty void instead of a row list. Added `.atlas-section.atlas-inbox.is-collapsed { flex: 0 0 auto }` so the flex-grow only applies while there's content to fill it. The bucket section doesn't need this (it was never flex-grown in the first place — PR 9 issue 3 was inbox-specific), so this override is scoped to `.atlas-inbox` only, not folded into the shared `.atlas-meta-children` rule.

## PR 10-18: grilled with Dan before any of them were built, not guessed at per-PR

**Decision:** before writing any code for this nine-PR batch (module modal fold/unfold, section-animation fixes, meta-folders-via-drop, meta-duplication, and the File Folder Status Sets port sliced across five PRs), the full design tree was interviewed with Dan directly across two rounds of numbered questions with recommended answers, following the `grill-me`/`grilling` process — rather than making the usual judgment calls solo and logging them after the fact the way PRs 1-9 did. ## PR 9: "Module" / "Folder" terminology swap — UI text only, internal code identifiers untouched

## PR 9: hover-during-drag-to-open-modal — accepted as best-effort, same risk tier as all drag work

**Decision:** issue 2's "hold a drag over a module without dropping to open its Contents modal, then drop into any nested location inside it" is being built to spec, at the same best-effort/unverified standard as every other drag-and-drop feature in this plugin — confirmed with Dan directly rather than assumed, after flagging that this is genuinely the most technically novel piece in this batch (a `Modal` opening *while* a native HTML5 drag is still active, itself becoming a live multi-target drop zone for that same in-flight drag) and that it inherits the same fundamental limitation as everything drag-related: no working synthetic HTML5 drag-and-drop in this container, so it can't be end-to-end verified here regardless of how carefully it's built. Reasoned through each edge case named in `TASKS.md` rather than only building the happy path, which is the most that can be done without a real drag input device.

## F8: real bug in the fold/unfold animation — rapid double-click got stuck instead of toggling back

**Decision:** caught in review (A11), not live testing — the chevron click handler computed `const collapsing = !node.collapsed`, reading the *data-model's* collapsed flag directly. That flag only actually updates once the deliberately-delayed (`META_COLLAPSE_TRANSITION_MS` = 160ms) `setNodeCollapsed` call runs and the resulting full re-render lands. A second click inside that 160ms window read the exact same unchanged `node.collapsed` value as the first click, so `collapsing` computed the identical direction both times — the row visibly got stuck (re-applying "collapse" twice, say, instead of collapse-then-expand) rather than alternating each click the way every other toggle in the UI does.

**Fix:** track the collapsed/expanded state as a local `let localCollapsed` variable scoped to that row's own click handler (initialized from `node.collapsed`, but from then on only ever updated by flipping its own prior value on each click — never re-read from the data model until the eventual full re-render replaces the whole closure anyway), and clear/reschedule the pending `setNodeCollapsed` timeout on every click rather than letting multiple stacked timeouts fire independently. Both were needed: the local variable fixes the "reads stale state" bug directly; the timeout cancellation means only the *last* click in a rapid burst ever gets persisted, so a quick collapse→expand→collapse doesn't also briefly persist and re-render the intermediate "expand" state before landing on the final one.

**Verified live** (this one doesn't need drag input, just clicks): a rapid two-click burst on the same chevron now correctly returns to the starting icon/state instead of getting stuck: from collapsed, two quick clicks land back on collapsed (confirmed via zoomed screenshots of the chevron icon before/after); a single click still toggles normally. No console errors either state.

## F8: "add to module" — the one deliberate disk-mutating exception, and why it doesn't force-promote

**Decision:** dropping a file or block directly onto a folder-unit row now offers (via a toggleable `ConfirmModal`) to physically move the underlying file into that folder on disk via `fileManager.renameFile` — the single exception, anywhere in this plugin, to "Atlas never touches disk for arrangement." Requested directly by Dan during his own first hands-on drag-and-drop pass (the one thing this build's container could never exercise itself), not something built speculatively.

**Confirmed before writing any code, not guessed:** since this cuts directly against a rule verified by grep in every single PR review this whole build, I asked two clarifying questions rather than assume: (1) does confirming actually move the file, or something non-disk-touching? (2) does the settings toggle gate the confirmation only, or the whole feature? Answers: yes, physically move it, but only keep it as a distinct, addressable Atlas unit if it *already* has real backlinks from outside the module — no forced manual promotion — and the toggle controls only whether the confirmation dialog appears, not whether the move happens at all.

**Why no forced promotion is the right implementation, not just the requested one:** it's the only choice consistent with the rest of the model. A promoted-file unit is defined everywhere else in this codebase by having a real inbound link from outside its top-level folder — manufacturing a promotion here (the way the F3 "promote an internal" drag path deliberately does, a different, existing, unrelated mechanism this doesn't touch) would make "add to module" secretly behave like promotion via a completely different, disk-mutating gesture. Letting the *existing* link-graph recompute decide is not just simpler, it's the only version where a file's promoted status always means the same thing regardless of how it got there.

**How it actually resolves without new promotion logic:** `fileManager.renameFile` fires Obsidian's normal `rename` event, which this plugin already wires end-to-end — `viewsManager.onVaultRename` rewrites any existing bucket placement's ref to the new path, and (once Obsidian's own metadataCache re-settles, since other files' link text needs to catch up to the move first) `unitIndex`'s ordinary `computePromotions()` naturally reclassifies the file as `promoted-file` if a real backlink survived the move. No manual-promotion call was added. A one-time `metadataCache.on("resolved")` listener (registered at drop time, unsubscribing itself on first fire) checks after that settling whether the file is still a recognized unit; if not, that ref is proactively unplaced rather than left rendering as a confusing "(missing)" ghost caused by the user's own deliberate action (as opposed to the F9 missing-ref case, which is specifically about *unexpected* external changes and correctly stays visible-and-recoverable).

**Cleanup scope, corrected per review (A11):** the first version only unplaced the ref from whichever single view the drag originated in, leaving stale ghosts in any *other* view that also happened to have it placed. Caught in review, and the fix is a real scope correction, not a style nit: the file moved on disk for the whole vault, not "within" whichever view happened to be on screen during the drag, so losing unit status is a vault-wide fact — the same way `onVaultRename`'s own ref-rewriting already treats a path change as cross-view, not scoped to one view's context. Now iterates every view and unplaces the (idempotent, no-op-if-absent) ref from each.

**Scoped to file/block payloads only:** dropping one folder-unit onto another falls back to the existing sibling-insert behavior untouched — moving an entire folder's contents and internals wholesale is a materially bigger operation than what was asked, and not attempted here.

**What's unverified:** everything drag-related in this build has the same ceiling — no working synthetic HTML5 drag-and-drop in this container. This feature additionally needs a real backlink scenario to exercise both outcomes (promoted vs. not), which is even less reachable without live testing than a plain placement drag. Confirmed only that the code path is reachable and type-checks, and reasoned through the event-ordering (rename-triggered `viewsManager`/`unitIndex` listeners are registered before this feature's own listener, so `getUnits()` reflects the settled state by the time it's checked) rather than assuming it.

## F8: bucket-root drop target was often unreachable, and meta-folder icons were 4px misaligned — both real bugs from Dan's live testing

**Decision (drop target):** `makeDropZone`'s `bucket-root` registration moved from `.atlas-node-list` (a div whose height hugs its content in normal block flow) to the whole bucket section container. Once the list had a few rows, there was almost no empty space left within the list div itself to register a drop on — a drop landing just past the last row missed every registered target entirely, landing on the un-instrumented parent instead. Any specific row still wins first via its own handler's `stopPropagation`, so this only widens the *fallback* target, it doesn't change what a drop onto an existing row does. Added 16px of trailing padding to the list too, so there's always a visually obvious strip of empty space to aim for, not just a technically-reachable-but-invisible one.

**Decision (icon alignment):** traced the exact pixel math rather than eyeballing a fix — a meta row's icon sits `.atlas-chevron`'s width (14px) + `.atlas-row`'s `gap` (6px) = 20px past the row's padding-left edge; a plain unit row has no chevron, so its own compensating offset needs to equal that same 20px to land in the same place. It was 16, four pixels short — exactly the "sits a few pixels right" Dan described. Fixed by correcting the constant (`UNIT_ROW_CHEVRON_OFFSET = 20`) rather than adding an ad-hoc margin, so it stays anchored to the actual chevron/gap values instead of drifting out of sync with them again.

**Decision (fold/unfold animation):** added a reveal transition for meta-folder collapse/expand, matching Obsidian's native file-tree feel, using the `grid-template-rows: 1fr → 0fr` technique — the standard CSS-only way to animate to/from an implicit `auto` height without JS-measuring `scrollHeight`. This required a real structural change: meta-folder children now always render into a dedicated `.atlas-meta-children` wrapper (previously they were only rendered into the DOM at all when expanded, as flat indented siblings of everything else — there was no per-folder element to animate). The chevron click now does two things in sequence rather than one: it toggles the wrapper's CSS class immediately (for the animation to actually play), and only *then*, delayed by the transition's own duration (`META_COLLAPSE_TRANSITION_MS`, kept in sync with the CSS `transition-duration` by comment, not shared code — a minor duplication accepted for simplicity), calls the state-persisting `setNodeCollapsed`. The delay matters because that call triggers this view's usual full `render()` teardown-and-rebuild; doing it immediately would rebuild the DOM from scratch on the very next tick and cut the animation short with a hard snap instead of a slide.

**What's verified vs. not, for both:** the drop-target fix's actual reachability needs Dan's own drag input to confirm, same as everything drag-related in this build — I can't drag-test it myself. The icon alignment fix was verified directly via a zoomed live screenshot (Bets/To Do/Ideas icons now share one vertical line). The animation was verified to produce no console errors and correct end-states on toggle, but not that the motion itself looks smooth — that's inherently something only real eyes watching real motion can confirm, not something a static screenshot comparison can settle.

## F8: keyboard Delete unplaces without a confirmation step — deliberate, not an oversight

**Decision:** `handleRowKeydown`'s `Delete` case calls `unplaceUnit` immediately, with no `ConfirmModal` in between — unlike "Delete view" and "Delete meta folder," which do confirm first.

**Why no confirm here specifically (per review, A8/A9):** unplacing a unit isn't destructive under this model — the unit doesn't disappear, it just returns to the inbox (its own view, or the global one), fully recoverable with the same "Place in view…" flow used to place it in the first place. Nothing on disk changes and no data is lost. Both "Delete view" and "Delete meta folder" *do* confirm (`ConfirmModal`, `showMetaFolderMenu`) even though neither is destructive either in the same disk-safety sense — their placements/children survive (moved to the global inbox, or up one level). The distinguishing factor isn't destructiveness, it's blast radius: those two actions can reshuffle however many placements or children a view/meta-folder holds in one keystroke, where Delete-to-unplace only ever touches the one row under the cursor. A confirmation step earns its place when an action's effect is large or hard to visually verify after the fact, not merely when something is technically reversible; a single-row, single-target action doesn't clear that bar the way a whole-view or whole-folder action does.

**What this means for the spec's "Delete to remove (with confirm)" wording:** read as describing the general shape of a delete-like action in the explorer, not a literal requirement that this specific keyboard shortcut must always confirm — the shape holds (actions with meaningful blast radius confirm; a single-row unplace doesn't have one).

## F8: real bug fixed post-review (A6) — drop-onto-nested-unit escaped to bucket root

**Decision:** `handleDrop`'s branch for "dropped onto a unit node, not a meta folder" (the Part 4 edge case where dropping a unit onto another unit should insert it as a sibling right after the target) hardcoded `parentId = null` regardless of where the target unit actually lived in the tree. `indexInParent` already did the equivalent recursive search to find the right *index* within whatever array the target lives in; this branch just never did the analogous lookup for the right *parent*. Fixed by adding `parentIdOf` — a recursive search returning the id of the meta folder a node lives in, or `null` for the bucket root — and using its result instead of the hardcoded `null`.

**How this was caught:** code review (A6), not live testing — dropping a unit onto another unit that's nested inside a meta folder would incorrectly escape the dropped unit out to the bucket root instead of landing inside that same meta folder as a sibling. This is exactly the failure mode the drag-and-drop-untestable-in-this-container limitation was hiding: none of the non-drag equivalents used throughout this build to verify `placeUnit`/`unplaceUnit` (the "Place in view…" flow, the temporary debug command, "Remove from view") exercise this specific branch of `handleDrop`, because they all call `placeUnit` directly with an already-correct `parentId` rather than going through the target-node → parent-lookup logic this bug lived in. A reminder that "verified the underlying method works" and "verified the UI computes the right arguments to it" are different claims — this build's non-drag substitutes covered the former, not the latter, for this one code path.

**Not separately live-tested even now** — still blocked on the same environment limitation (no working synthetic drag in this container) — but it's now correct by code inspection rather than silently wrong underneath a passing-looking test suite. Real drag-and-drop testing (per A7's recommendation) is the one item in this build genuinely best left for Dan's own hands-on pass.

## F11: scale test — real bugs found and fixed, not just a passing benchmark

**Decision:** scripted 5,050 root-file units + 2,000 free blocks directly into the fixture vault (rather than a separate scratch vault — this vault is already a disposable Atlas-testing fixture, see the "pangyo" note elsewhere in this log) to reach 7,075 total units from a 75-unit baseline, then measured and fixed what broke rather than just confirming the AC's number.

**Two real performance bugs found, not hypothetical ones:**
1. `resolveRef` (`explorer-view.ts`) did `this.plugin.unitIndex.getUnits().find(...)` — an O(n) linear scan — for every row resolved, and the inbox resolves every unit on every render to filter/sort it. That's O(n²) per render. At 75 units this is invisible (5,625 comparisons); at 7,075 units it's ~50 million, easily enough to make the UI feel broken even though nothing was logically wrong. Fixed by building a `Map<string, Unit>` (`unitsByRefKey`) once per `render()` call and using it for O(1) lookups — turns the whole render into O(n).
2. Free-block display text was read fresh from disk (`getFreeBlockDisplayText`) on every single render pass for every free-block unit, even though F7 already built and vault-event-maintains a `FreeBlockTextCache` for exactly this text. `resolveUnit` now takes that cache as an optional parameter and serves from it first, falling back to a fresh read only on a cache miss. `main.ts`'s `freeBlockTextCache` field was made public so the explorer could reach it.

**The virtualization design (inbox only, not the bucket):** the inbox renders inside a bounded, independently-scrollable viewport (`max-height: 45vh`) with fixed-row-height windowing — only the rows within the scrolled range (+ overscan) are ever real DOM nodes, positioned via `top` offset inside a full-height spacer so the scrollbar reflects the true list length. Redraws are `requestAnimationFrame`-throttled on the viewport's own `scroll` event, not routed through the view's full `render()` (which would re-resolve/re-sort/re-render the toolbar and bucket on every scroll tick). The bucket tree is left un-virtualized: it's user-curated, not vault-sized, and giving it its own bounded viewport too would be solving a problem it doesn't have. **Named scope boundary:** expanding a folder-unit's internals (F3) needs normal variable-height document flow, which the fixed-row-height virtualized path can't represent, so virtualization is skipped entirely for that render pass when any folder is expanded. That's a deliberate, occasional-and-bounded fallback (one folder's contents, not the whole vault), not a gap in the thousands-of-rows case that actually needs protecting.

**Fixed row height is an assumption, not a measurement:** `INBOX_ROW_HEIGHT = 28` is a constant, not measured from the real rendered DOM. All inbox rows are single-line (`white-space: nowrap`, no wrapping content), so this holds in practice, but it's worth naming as a simplification rather than pretending it's derived.

**A real, scale-independent bug found along the way, not a scale-specific one:** the filter box lost keyboard focus after every keystroke, at *any* list size — `render()` empties and rebuilds the entire container, including the filter `<input>` itself, on every change (index update, view switch, *or* a filter keystroke, since typing calls `void this.render()` the same as everything else). The freshly-created input has no focus, so every keystroke past the first was silently discarded — this had been true since F8 shipped, just easy to miss with small lists where a one-character filter often still "worked" well enough to look intentional. Fixed by capturing `document.activeElement` and the filter input's caret position before `container.empty()`, and restoring both on the new input afterward.

**Environment finding, recorded so it isn't mistaken for an Atlas bug in a future scale test:** bulk-creating thousands of files directly on the host filesystem while the container's Obsidian instance is running does not reliably reach Obsidian's own vault index via this Docker bind mount's file watcher — repeated `Atlas: Rebuild index` runs under-counted for over a minute after file generation had finished on disk (175 → 286 → 1253 → 3120 → 4625, then stalled well short of 7,075). A `Reload app without saving` (forcing Obsidian's real startup-time full vault scan) picked up every file correctly on the first try. Atlas's index is only ever as complete as `app.vault.getFiles()` reports; if Obsidian's own watcher hasn't caught up, no amount of correct `create`/`delete` event handling in Atlas can compensate. Same class of issue as the earlier-documented external-rename-not-firing gap — a Docker bind-mount file-watching limitation, not something a real (non-containerized) install would hit.

**The actual numbers, for the record:** `[Atlas] full index rebuild in 18.0ms (7075 units)` (`{"folder-unit":24,"root-file":5050,"free-block":2000,"promoted-file":1}`), incremental promotion recompute consistently 4.5–6ms per event (1636 links scanned) throughout. Both comfortably clear the spec's "<2s full rebuild, <100ms incremental" bar at scale — F2's original measurements (2.6–13ms full rebuild at 75 units) hadn't actually been checked against a vault big enough for the target to be meaningful until now.

**Cleanup:** all 7,075 scratch files were deleted after measuring, confirmed via `git status` (clean) and a rebuilt index matching the exact pre-test 75-unit baseline (`{"folder-unit":24,"root-file":50,"promoted-file":1}`, byte-for-byte the same breakdown).

## F6: self-calibrating suggestion sort (post-PR-4 review A4, refined post-PR-5 review A5)

**Decision (final form):** a unit (`folder-unit`/`free-block`/`promoted-block`) only sorts above plain `file` matches when its own fuzzy-match score is at least as good as the best `file`-kind score in that same result set. Otherwise it's sorted by score alongside files, same as before. No fixed tier, no magic-number margin — the threshold is the query's own best file match, recomputed per query.

**How this evolved (two rounds, both driven by live evidence, not review-only back-and-forth):**
1. **A4** caught that "`[[bets` surfaces the `Bets` folder-unit" was checked off but not actually guaranteed — pure fuzzy-score sort meant a real competing file (e.g. `Bets/notes-on-bets.md`) could out-rank the folder-unit. First fix: an unconditional kind tier (all units always outrank all files). Verified live, closed the gap.
2. **A5** pushed back on that fix after seeing its own live evidence: the unconditional tier meant *any* unit, however weak its match, now outranked *every* file. Confirmed live: typing `bets` surfaced `Kubernetes` and `Objectives` — both incidental weak subsequence matches — above an exact-ish `bets` filename match. The reviewer judged this a bigger behavior change than the hand-off doc's two narrow examples called for, and asked for a margin/threshold instead, suggesting the self-calibrating form specifically to avoid picking an arbitrary constant.

**Why the self-calibrating form over a fixed margin:** a fixed threshold (e.g. "unit score must be within 10 points of the best file score") requires guessing a constant with no principled value, and would need re-tuning if Obsidian's fuzzy-search scoring ever changes. Comparing directly against the best file score in the same query's result set has no constant to pick and degrades sensibly (no files matched → every unit clears the bar trivially, since there's nothing to bury).

**Verified live, both directions, with the same fixture file (`Bets/notes-on-bets.md`) that exposed the original gap:** `Bets`/folder still sorts first (its match against "bets" is competitive with the best file match) — the case A4 cared about. `Kubernetes`/`Objectives` no longer outrank the exact `bets`/`Bets` file matches — the case A5 cared about. Both confirmed in the same test run, not assumed from the code alone.

## MCP node addressing for API/CSV/markdown-table placeholder rows (PR-2.F1, review R1)

**Decision:** a placeholder row's MCP-visible `id` is an owner-qualified composite — `apiItemAddress(ownerNodeId, rowId)`, implemented as `` `${ownerNodeId}::${rowId}` `` — not the bare `ApiItemState.id`/`unitRefKey(ref)` the row carries internally. `list_nodes` reports this composite id for every placeholder row, and `get_node_status`/`set_node_status` accept it as `nodeId`. A bare, non-composite row id (e.g. the old `"row-1"`) no longer resolves to anything and is refused with the same "not found" error an unknown id gets. Real `ViewNode`s (files, folders, blocks, modules) keep using their own `node.id` directly — composite addressing applies only to synthetic placeholder rows, which are the only case where one raw id can legitimately appear under two different owners in the same view (two Folders/CSVs on the same or a duplicated source, both keyed by the same external row id or row number).

For a block's own address — distinct from a placeholder row's — the existing, unchanged convention is the file path plus a `#subpath` fragment (e.g. `Notes/Daily.md#^block-id` or `Notes/Daily.md#Heading`), matching Obsidian's own link-subpath syntax; `extractMcpAddress` already parsed this form before this PR and nothing about it changed here.

As a second, defense-in-depth layer (not a substitute for composite addressing, since two different *real* `ViewNode`s should never legitimately share an `id` at all): `resolveMcpAddress`'s node-id lookup now collects every match for a given id rather than returning the first one with `.find()`, and throws `McpAmbiguousNodeIdError` — listing each match with its owning view/ancestors, the same way an ambiguous path is refused — if more than one is found. In normal operation this should never fire for real nodes; it exists purely so a corrupt or hand-edited `data.json` can never cause a silent write to the wrong target.

**Why:** review R1 on this PR traced a real silent-wrong-write path — `resolveMcpAddress` matched placeholder rows by their bare id, which is unique only within one owner, so `set_node_status("1", ...)` against two Folders/CSVs that both have a row `"1"` always wrote the first owner's row even when the agent meant the second, with no error at all. Composite addressing removes the collision at the source (the id `list_nodes` hands back is already disambiguated) rather than only detecting it after the fact.

## MCP row visibility mirrors the explorer's render rules (PR-2.F1, review R3)

**Decision:** `resolveMcpAddress`/`walkView`/the tools' child-listing now take an optional `McpRowVisibility` (`{ isHidden, isUnresolvedOutside }`), built per-call by `buildRowVisibility` in `mcp-status-tools.ts` from the real `ViewsManager`/`FolderSourcePathStore`, not a reimplementation:
- `isHidden(node)` is `viewsManager.managedRowFilterState(view.id, node) === "hidden"` — the same YAML-rule-driven hide decision the explorer renders.
- `isUnresolvedOutside(node)` checks `node.folderSourceManaged`/`folderSourceOwnerId`, confirms the owner's Folder source is `location: "outside"`, and that `resolveOutsidePath` can't resolve a path on this device — the same check `ExplorerView.isOutsideManagedAndUnresolved` makes.

A hidden row is refused as a target (not found) but its children are still reachable, lifted with the hidden row appended as their *furthest* ancestor (`[...ancestors, hiddenNode]`) — so a closer, still-visible governor keeps winning the way it does on screen, matching `ExplorerView.visibleFolderSourceRows`'s own lift order exactly rather than the walk's previous `[node, ...ancestors]` (nearest-first) order. An unresolved Outside-Vault-managed row drops its entire subtree instead (no lift — it renders as if it doesn't exist on this device). Callers that don't pass a visibility (none remain in production code; some low-level resolver unit tests do, deliberately, to pin the pre-R3 default) get `alwaysVisible`, which treats every row as shown.

**Why:** review R3 found that `walkView`/`summarizeNode` always used `[node, ...ancestors]` and never checked hidden/unresolved state at all, so `list_nodes`/`get_node_status` could report — and `set_node_status` could accept a write against — a row the explorer never renders, and could resolve against a hidden governor's status set when the UI would have resolved against the next visible one (or none). Reusing `ViewsManager.managedRowFilterState` and the Outside-Vault resolution check, rather than re-deriving the rule, keeps the two guaranteed in sync as the explorer's own rule evolves.

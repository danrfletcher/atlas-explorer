  **Two more real bugs, both found by Dan's own hands-on testing (not caught by this PR's CDP testing), both fixed same-day:**
  1. **Inbox → bucket drag stopped working entirely.** Root cause: `buildNodeDragPayload`/`buildInboxDragPayload` called `void this.render()` from inside a `dragstart` handler to reset the selection to a single item when dragging something not already selected — but `render()`'s `container.empty()` tears the dragged row itself out of the document a moment into its own drag gesture, which reliably aborts a real native HTML5 drag in Chromium. CDP's synthetic `dispatchEvent(new DragEvent(...))` doesn't route through the browser's actual native drag state machine, so every drag test this PR ran passed regardless — only a real mouse hit it. Fixed by dropping the render call from both builders entirely; the selection `Set`s still update correctly (silently), and the visible highlight catches up on the very next render, which `handleDrop` already triggers right after the drop completes. Verified live: the dragged row's `isConnected`/`document.body.contains(...)` now stay `true` immediately after `dragstart` (previously the render would have detached it at exactly this point), and a full inbox→bucket drag+drop completes correctly end to end again.
  2. **Clicking a row scrolled deep into the inbox jumped the whole list back to the top — a recurring pattern Dan flagged across several PRs, not new to this one.** Root cause: `render()` only ever captured/restored the *outer* sidebar's `container.scrollTop`; the inbox's own virtualized viewport (F11, `.atlas-inbox-viewport`) is a second, independent `overflow-y: auto` scroll context, rebuilt from scratch by `container.empty()` with nothing capturing or restoring *its* scroll position at all. This bug predates PR 20 (the filter box already re-rendered on every keystroke), but PR 20 made it dramatically more noticeable — a plain click on an inbox row never triggered a re-render *at all* before this PR, so selecting something while scrolled down in a large inbox is a brand-new, very common way to hit it. Fixed by capturing `.atlas-inbox-viewport`'s `scrollTop` in `render()` before `container.empty()`, threading it through `renderInboxSection`/`renderVirtualizedInboxRows`, and applying it to the freshly-created viewport *before* its first `drawWindow()` call (which reads `scrollTop` synchronously to decide the initial render window — setting it after would draw the wrong rows first and only self-correct on the next scroll). Verified live: scrolled the inbox to 400px, clicked a row in view, confirmed `scrollTop` was still 400 immediately after the re-render, and confirmed visually via screenshot.

  **Reviewer follow-up (A27), one more branch of the same bug family, fixed same-day:** dropping the `dragstart` render call (fix #1 above) leaves `handleDrop`'s own render as the only remaining repaint trigger — correct for a successful drop, but an *abandoned* drag (dropped outside any registered zone, or cancelled) never reaches `handleDrop` at all, so its silent selection-reset would never actually get painted. The existing window-level `dragend` backstop (added earlier in the build to always clear `dragPayload` regardless of how a drag ends) already fires unconditionally either way — added `this.queueRender()` there too, so the visual state always eventually catches up. Verified live: dragging an unselected row and abandoning the drag (dispatching `dragend` with no prior `drop`) leaves the selection state correct-but-unpainted immediately, then correctly painted (`is-selected` present) shortly after.

  **Reviewer follow-up, same round, caught a factual error in that fix's own reasoning:** the first version claimed `queueRender` would "coalesce into the same repaint as a same-tick `handleDrop` call" — but `handleDrop` called `void this.render()` directly (same pattern used a dozen+ other places in this file), which never touches `queueRender`'s own dedup flag, so the two never actually coalesced; a successful drop was silently doing two render passes, harmless but not what the comment claimed. Fixed for real, not just re-worded: both of `handleDrop`'s own render call sites now go through `queueRender()` too, so the flag the `dragend` fix relies on is genuinely shared. Verified live by instrumenting `render()` with a call counter across a full drop+dragend sequence — first attempt (an artificial 30ms gap between dispatching `drop` and `dragend`, to mimic realistic timing per this build's own established lesson about too-fast synthetic dispatch) came back as 2 renders, which looked like the fix hadn't worked; traced it correctly instead of taking that at face value — a real browser dispatches `drop` then `dragend` essentially back-to-back with no such gap, so the *test's* artificial delay was long enough for the first `setTimeout(0)`-deferred render to already fire and reset the flag before `dragend`'s own call arrived, the mirror-image of the earlier too-fast-dispatch artifact in this same build. ### Running the E6 relay (`scripts/tephra-relay.mjs`)

A dev script, outside `src/` and not bundled into `main.js`. It sits between Obsidian and the real `tephrad`:

- Plain HTTP calls (the JSON-RPC `POST /rpc`) are forwarded to `tephrad` and the reply returned as it came. Only `Host` is rewritten to name `tephrad`. Nothing in a body or header is read, changed or logged.
- The push channel (the WebSocket upgrade on `GET /rpc`) is answered by the relay itself and never reaches `tephrad`. It sends nothing until it is signalled, then one `graph:changed` text frame to each connected push client. It only requires an `Authorization` header on that upgrade; `tephrad` still checks the token on every forwarded call.
- It binds `127.0.0.1` only (relay port and the optional control port) and refuses a `--target` that isn't an `http://` loopback address with an explicit port.

Run it (pick free scratch ports, not Tephra's default 4812):

```
node scripts/tephra-relay.mjs --target http://127.0.0.1:<tephrad-port> --port <relay-port> [--control-port <port>]
```

It prints its PID and ports. Set `"tephraUrl": "http://127.0.0.1:<relay-port>"` in `settings` in the plugin's `data.json` (see docs/settings.md) and reload the plugin. Send the frame with any of: `kill -USR1 <relay pid>`, a line `push` on the relay's stdin, or `curl -X POST http://127.0.0.1:<control-port>/push` (200 with the client count, 409 when no push client is connected). Every frame is logged with an ISO timestamp and the words "stand-in push": the frame is the one thing real Tephra doesn't send for a `source add` or `remove`, so keep that wording in any evidence log. Stop it with Ctrl-C or `kill <pid>` (only the PID you started).
